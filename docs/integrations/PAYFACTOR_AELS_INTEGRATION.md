# PayFactor AELS Integration Guide

This document provides a comprehensive guide for PayFactor to integrate with PaySurity for managing payments related to AELS (Automated Escrow & Ledger System) transactions, leveraging a 2-tranche escrow model.

## Overview

The PayFactor AELS integration enables secure, managed payments for transactions requiring an escrow service with two distinct payment stages. This ensures that funds are held securely until specific conditions are met, protecting both the buyer and the seller. PaySurity acts as the escrow agent, facilitating the deposit, holding, and release or refund of funds based on triggers from AELS (via PayFactor).

Key features of this integration include:
*   **2-Tranche Escrow**: A payment mechanism involving an initial deposit (Tranche 1) and a final payment (Tranche 2).
*   **Secure Fund Holding**: Funds are held in a secure escrow account until transaction conditions are met.
*   **Automated Releases/Refunds**: API-driven mechanisms to release funds to the seller or refund the buyer.
*   **Real-time Status Updates**: Webhooks provide immediate notifications on transaction lifecycle events.
*   **HMAC Security**: All API interactions are secured using HMAC signatures to ensure data integrity and authenticity.

## How it works (2-Tranche Escrow)

The AELS 2-tranche escrow process manages the flow of funds from a buyer to a seller through two distinct payment stages.

1.  **Transaction Initiation**: AELS (via PayFactor) initiates an escrow transaction on PaySurity, specifying the total transaction amount, buyer, seller, and a unique identifier. This creates the escrow account.
2.  **Tranche 1 Deposit (Initial Payment)**: The buyer makes an initial deposit, representing Tranche 1, into the PaySurity escrow account. This typically secures the deal or covers initial costs. The transaction moves to an `ESCROW_TR1_FUNDED` state.
3.  **Intermediate Phase**: After Tranche 1 is funded, there's a period where the terms of the deal are fulfilled (e.g., service delivery, product manufacturing). During this phase, funds remain in escrow.
4.  **Tranche 2 Deposit (Final Payment)**: Upon successful completion of the agreed-upon terms, the buyer makes the final payment, Tranche 2, into the same PaySurity escrow account. The transaction moves to an `ESCROW_TR2_FUNDED` state.
5.  **Funds Release**: Once both Tranche 1 and Tranche 2 are deposited and all conditions for the transaction are met (as determined by AELS), PayFactor instructs PaySurity to release the full amount (Tranche 1 + Tranche 2) to the seller. The transaction moves to a `COMPLETED` state.
6.  **Refund Scenarios**:
    *   **Refund Tranche 1**: If the deal falls through *before* Tranche 2 is deposited, PayFactor can instruct PaySurity to refund Tranche 1 to the buyer. The transaction moves to a `REFUNDED_TR1` state.
    *   **Full Refund (less common)**: In rare cases, if both tranches are deposited but the deal is irrevocably cancelled before funds release, a full refund might be initiated. This requires specific business logic approval and moves to a `REFUNDED_FULL` state.

Throughout this process, PaySurity sends webhook notifications to PayFactor on significant state changes, keeping AELS updated on the payment lifecycle.

## API Endpoints

All API requests must include `X-PaySurity-Tenant-Id`, `X-PaySurity-API-Key`, and `X-PaySurity-HMAC-Signature` headers. `{{BASE_URL}}` refers to the PaySurity API endpoint (e.g., `https://api.paysurity.com`).

### 1. Create AELS Escrow Transaction

Initiates a new 2-tranche escrow transaction.

*   **Endpoint**: `POST /integrations/payfactor/aels/escrows`
*   **Description**: Creates an escrow record, assigning a unique `escrowId`.
*   **Request Body**:
    ```json
    {
        "externalRefId": "AELS-TXN-123456",
        "totalAmount": 1500.00,
        "tranche1Amount": 500.00,
        "currency": "USD",
        "buyerDetails": {
            "email": "buyer@example.com",
            "name": "John Doe",
            "externalId": "BUYER-EXT-ID-1"
        },
        "sellerDetails": {
            "email": "seller@example.com",
            "name": "Jane Smith",
            "externalId": "SELLER-EXT-ID-1",
            "payoutMethod": {
                "type": "BANK_TRANSFER",
                "accountNumber": "123456789",
                "routingNumber": "987654321",
                "bankName": "Example Bank",
                "accountHolderName": "Jane Smith"
            }
        },
        "description": "Payment for AELS project Alpha - Phase 1"
    }
    ```
*   **Response Body (201 Created)**:
    ```json
    {
        "escrowId": "es_uuid_12345",
        "externalRefId": "AELS-TXN-123456",
        "status": "CREATED",
        "totalAmount": 1500.00,
        "tranche1Amount": 500.00,
        "currency": "USD",
        "buyerDetails": {
            "email": "buyer@example.com",
            "name": "John Doe",
            "externalId": "BUYER-EXT-ID-1"
        },
        "sellerDetails": {
            "email": "seller@example.com",
            "name": "Jane Smith",
            "externalId": "SELLER-EXT-ID-1"
        },
        "createdAt": "2023-10-26T10:00:00Z"
    }
    ```
*   **Curl Example**:
    ```bash
    curl -X POST "{{BASE_URL}}/integrations/payfactor/aels/escrows" \
      -H "Content-Type: application/json" \
      -H "X-PaySurity-Tenant-Id: {{TENANT_ID}}" \
      -H "X-PaySurity-API-Key: {{API_KEY}}" \
      -H "X-PaySurity-HMAC-Signature: {{HMAC_SIGNATURE}}" \
      -d '{
            "externalRefId": "AELS-TXN-123456",
            "totalAmount": 1500.00,
            "tranche1Amount": 500.00,
            "currency": "USD",
            "buyerDetails": {
                "email": "buyer@example.com",

            "description": "Payment for AELS project Alpha - Phase 1"
    ```

### 2. Deposit Tranche 1

Records the successful deposit of Tranche 1 funds into escrow. This is typically called after the buyer's payment system confirms receipt of funds for Tranche 1.

*   **Endpoint**: `POST /integrations/payfactor/aels/escrows/{escrowId}/deposit-tranche1`
*   **Description**: Marks Tranche 1 as deposited. The `depositAmount` must match the `tranche1Amount` specified during escrow creation.
*   **Request Body**:
    ```json
    {
        "depositAmount": 500.00,
        "paymentProcessorRefId": "PP-TR1-REF-7890",
        "depositDate": "2023-10-26T10:15:00Z"
    }
    ```
*   **Response Body (200 OK)**:
    ```json
    {
        "escrowId": "es_uuid_12345",
        "status": "ESCROW_TR1_FUNDED",
        "fundedAmount": 500.00,
        "tranche1DepositRefId": "PP-TR1-REF-7890",
        "updatedAt": "2023-10-26T10:15:00Z"
    }
    ```
*   **Curl Example**:
    ```bash
    curl -X POST "{{BASE_URL}}/integrations/payfactor/aels/escrows/es_uuid_12345/deposit-tranche1" \
      -H "Content-Type: application/json" \
      -H "X-PaySurity-Tenant-Id: {{TENANT_ID}}" \
      -H "X-PaySurity-API-Key: {{API_KEY}}" \
      -H "X-PaySurity-HMAC-Signature: {{HMAC_SIGNATURE}}" \
      -d '{
            "depositAmount": 500.00,
            "paymentProcessorRefId": "PP-TR1-REF-7890",
            "depositDate": "2023-10-26T10:15:00Z"
          }'
    ```

### 3. Deposit Tranche 2

Records the successful deposit of Tranche 2 funds into escrow. This is called after the buyer's payment system confirms receipt of funds for Tranche 2.

*   **Endpoint**: `POST /integrations/payfactor/aels/escrows/{escrowId}/deposit-tranche2`
*   **Description**: Marks Tranche 2 as deposited. The `depositAmount` should be `totalAmount - tranche1Amount`.

    ```json
        "depositDate": "2023-10-27T14:30:00Z"
    ```

    ```json
        "escrowId": "es_uuid_12345",
        "status": "ESCROW_TR2_FUNDED",
        "fundedAmount": 1500.00,
        "tranche2DepositRefId": "PP-TR2-REF-1122",
        "updatedAt": "2023-10-27T14:30:00Z"
    }
    ```
*   **Curl Example**:
    ```bash
    curl -X POST "{{BASE_URL}}/integrations/payfactor/aels/escrows/es_uuid_12345/deposit-tranche2" \
      -H "Content-Type: application/json" \
      -H "X-PaySurity-Tenant-Id: {{TENANT_ID}}" \

            "depositAmount": 1000.00,
            "paymentProcessorRefId": "PP-TR2-REF-1122",
            "depositDate": "2023-10-27T14:30:00Z"
          }'
    ```

### 4. Release Funds to Seller

Instructs PaySurity to release the full escrowed amount to the seller's configured payout method. This can only occur if both Tranche 1 and Tranche 2 have been deposited.

*   **Endpoint**: `POST /integrations/payfactor/aels/escrows/{escrowId}/release`
*   **Description**: Initiates the payout to the seller.
*   **Request Body**:
    ```json
    {
        "releaseAmount": 1500.00,
        "releaseDate": "2023-10-28T11:00:00Z",
        "reason": "Contract terms fulfilled"
    }
    ```
*   **Response Body (200 OK)**:
    ```json
    {
        "escrowId": "es_uuid_12345",
        "status": "COMPLETED",
        "releasedAmount": 1500.00,
        "payoutId": "po_uuid_67890",
        "updatedAt": "2023-10-28T11:00:00Z"
    }
    ```
*   **Curl Example**:
    ```bash
    curl -X POST "{{BASE_URL}}/integrations/payfactor/aels/escrows/es_uuid_12345/release" \
      -H "Content-Type: application/json" \
      -H "X-PaySurity-Tenant-Id: {{TENANT_ID}}" \
      -H "X-PaySurity-API-Key: {{API_KEY}}" \
      -H "X-PaySurity-HMAC-Signature: {{HMAC_SIGNATURE}}" \
      -d '{
            "releaseAmount": 1500.00,
            "releaseDate": "2023-10-28T11:00:00Z",
            "reason": "Contract terms fulfilled"
          }'
    ```

### 5. Refund Tranche 1

Initiates a refund of Tranche 1 to the buyer. This is typically used when the deal falls through before Tranche 2 is paid.

*   **Endpoint**: `POST /integrations/payfactor/aels/escrows/{escrowId}/refund-tranche1`
*   **Description**: Refunds the deposited Tranche 1 amount to the buyer. Can only be performed if the transaction is in `ESCROW_TR1_FUNDED` state.
*   **Request Body**:
    ```json
    {
        "refundAmount": 500.00,
        "refundDate": "2023-10-27T09:00:00Z",
        "reason": "Buyer cancelled before Tranche 2"
    }
    ```
*   **Response Body (200 OK)**:
    ```json
    {
        "escrowId": "es_uuid_12345",
        "status": "REFUNDED_TR1",
        "refundedAmount": 500.00,
        "refundId": "rf_uuid_123",
        "updatedAt": "2023-10-27T09:00:00Z"
    }
    ```
*   **Curl Example**:
    ```bash
    curl -X POST "{{BASE_URL}}/integrations/payfactor/aels/escrows/es_uuid_12345/refund-tranche1" \
      -H "Content-Type: application/json" \
      -H "X-PaySurity-Tenant-Id: {{TENANT_ID}}" \
      -H "X-PaySurity-API-Key: {{API_KEY}}" \
      -H "X-PaySurity-HMAC-Signature: {{HMAC_SIGNATURE}}" \
      -d '{
            "refundAmount": 500.00,
            "refundDate": "2023-10-27T09:00:00Z",
            "reason": "Buyer cancelled before Tranche 2"
          }'
    ```

## HMAC Signing Instructions

All requests to PaySurity APIs require an HMAC-SHA256 signature for authentication and integrity verification. This ensures that the request originated from PayFactor and has not been tampered with.

### Signing Process

1.  **Generate a Timestamp**: Get the current UTC timestamp in ISO 8601 format (e.g., `2023-10-26T10:30:00Z`). This timestamp should also be sent in the `X-PaySurity-Timestamp` header.
2.  **Construct the Signing String**: Concatenate the following elements in order, separated by a newline character (`\n`):
    *   HTTP Method (uppercase, e.g., `POST`, `GET`).
    *   URL Path (e.g., `/integrations/payfactor/aels/escrows`).
    *   Canonical Query String (if any, alphabetically sorted by key, `key=value&key2=value2`). If no query parameters, use an empty string.
    *   `X-PaySurity-Timestamp` header value.
    *   `X-PaySurity-Tenant-Id` header value.
    *   SHA256 hash of the request body (hex encoded). If the request body is empty (e.g., GET requests with no body), use an empty string's SHA256 hash (e.g., `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`).
3.  **Calculate HMAC-SHA256**: Use your `API_SECRET` (provided by PaySurity) as the key to calculate the HMAC-SHA256 of the constructed signing string. The result should be hex encoded.
4.  **Add to Header**: Include the calculated HMAC signature in the `X-PaySurity-HMAC-Signature` header.

### Example for POST request

Assume:
*   `API_SECRET`: `your_secret_key`
*   `TENANT_ID`: `your_tenant_id`
*   `API_KEY`: `your_api_key`
*   `Timestamp`: `2023-10-26T10:30:00Z`
*   HTTP Method: `POST`
*   URL Path: `/integrations/payfactor/aels/escrows`
*   Request Body: `{"externalRefId": "AELS-TXN-123", "totalAmount": 100.00, "tranche1Amount": 50.00, "currency": "USD", "buyerDetails": {"email": "b@e.com"}, "sellerDetails": {"email": "s@e.com", "payoutMethod": {"type": "BANK_TRANSFER", "accountNumber": "123", "routingNumber": "123", "bankName": "Bank", "accountHolderName": "Seller"}}}`

1.  **Request Body SHA256**:
    `sha256("{\"externalRefId\": \"AELS-TXN-123\", \"totalAmount\": 100.00, \"tranche1Amount\": 50.00, \"currency\": \"USD\", \"buyerDetails\": {\"email\": \"b@e.com\"}, \"sellerDetails\": {\"email\": \"s@e.com\", \"payoutMethod\": {\"type\": \"BANK_TRANSFER\", \"accountNumber\": \"123\", \"routingNumber\": \"123\", \"bankName\": \"Bank\", \"accountHolderName\": \"Seller\"}}}")`
    (Let's assume this results in `body_hash_xyz`)

2.  **Signing String**:
    ```
    POST
    /integrations/payfactor/aels/escrows

    2023-10-26T10:30:00Z
    your_tenant_id
    body_hash_xyz
    ```
    *(Note the empty line for query string)*

3.  **HMAC-SHA256 Calculation**:
    `HMAC-SHA256(your_secret_key, signing_string)`
    (Let's assume this results in `calculated_hmac_signature`)

4.  **Headers**:
    ```
    X-PaySurity-Tenant-Id: your_tenant_id
    X-PaySurity-API-Key: your_api_key
    X-PaySurity-Timestamp: 2023-10-26T10:30:00Z
    X-PaySurity-HMAC-Signature: calculated_hmac_signature
    ```

### Important Notes:
*   The `X-PaySurity-Timestamp` must be within a small window (e.g., 5 minutes) of the server's time to prevent replay attacks.
*   Ensure the request body for hashing is exactly what is sent over the wire (no pretty-printing, consistent whitespace).
*   For GET requests without a body, the SHA256 hash of an empty string (`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`) should be used as the last element of the signing string.

## Overview

The PayFactor AELS (Automated Escrow & Ledger System) Integration on PaySurity facilitates a secure two-tranche escrow payment workflow, specifically designed for managing payments in complex transactions that involve stages of completion or verification. This integration allows PayFactor to programmatically manage the lifecycle of an AELS transaction from initial escrow creation to final fund release or refund, ensuring financial security for both buyers and sellers.

PaySurity acts as the trusted third-party escrow holder, providing API endpoints for PayFactor to control the flow of funds and webhooks to keep PayFactor informed of all critical payment events. This enables AELS to automate its financial operations, reducing manual intervention and potential for error.

## How it works (2-Tranche Escrow)

The 2-tranche escrow model is structured to manage payments for transactions that require an initial commitment followed by a final payment upon agreed-upon milestones or completion. Here's the typical lifecycle:

1.  **Escrow Creation**: PayFactor initiates an escrow transaction on PaySurity, defining the total transaction value and the breakdown into Tranche 1 (initial deposit) and Tranche 2 (final payment). This establishes the escrow account. The status is `CREATED`.
2.  **Tranche 1 Deposit**: The buyer deposits the Tranche 1 amount into the PaySurity escrow account. PayFactor confirms this deposit via an API call, and PaySurity updates the transaction status to `ESCROW_TR1_FUNDED`. This signifies the buyer's initial commitment.
3.  **Intermediate Phase / Work in Progress**: Funds for Tranche 1 are securely held in escrow. During this period, the seller typically commences work, delivers initial components, or meets preliminary milestones as defined by the AELS agreement.
4.  **Tranche 2 Deposit**: Once the agreed-upon conditions for the second tranche are met (e.g., project completion, service delivery confirmation), the buyer deposits the remaining Tranche 2 amount into the same PaySurity escrow account. PayFactor confirms this deposit, and PaySurity updates the transaction status to `ESCROW_TR2_FUNDED`.
5.  **Funds Release**: After both tranches are fully funded and all final conditions are satisfied (as verified by AELS/PayFactor), PayFactor triggers the release of the *entire* escrowed amount (Tranche 1 + Tranche 2) to the seller's designated payout method. The transaction status changes to `COMPLETED`.
6.  **Refund Scenarios**:
    *   **Tranche 1 Refund**: If the deal is cancelled *after* Tranche 1 has been deposited but *before* Tranche 2, PayFactor can initiate a refund of Tranche 1 to the buyer. The status becomes `REFUNDED_TR1`.
    *   **Full Refund (Rare)**: In exceptional circumstances, if the entire transaction is cancelled after both tranches are funded but before release, a full refund might be processed to the buyer. The status becomes `REFUNDED_FULL`. This scenario requires explicit approval and is managed on a case-by-case basis.

PaySurity communicates these state changes to PayFactor via webhooks, ensuring real-time synchronization.

## API Endpoints

All API requests must include the following custom headers for authentication and identification:
*   `X-PaySurity-Tenant-Id`: Your unique tenant identifier.
*   `X-PaySurity-API-Key`: Your API key, obtained from the PaySurity dashboard.
*   `X-PaySurity-Timestamp`: The UTC timestamp of the request in ISO 8601 format (e.g., `2023-10-26T10:30:00Z`).
*   `X-PaySurity-HMAC-Signature`: The HMAC-SHA256 signature of the request payload, as described in the HMAC signing instructions.

`{{BASE_URL}}` refers to the PaySurity API endpoint (e.g., `https://api.paysurity.com`).

## HMAC Signing Instructions

To ensure the authenticity and integrity of all API requests, PaySurity requires an HMAC-SHA256 signature for every incoming request. You will use your `API_SECRET` (provided by PaySurity) as the secret key for signing.

### Steps to Generate an HMAC Signature:

1.  **Retrieve API Credentials**: Ensure you have your `X-PaySurity-Tenant-Id`, `X-PaySurity-API-Key`, and the corresponding `API_SECRET`.
2.  **Generate a Timestamp**: Obtain the current UTC timestamp in ISO 8601 format (e.g., `2023-10-26T10:30:00.000Z`). This exact timestamp must be sent in the `X-PaySurity-Timestamp` header.
3.  **Prepare Request Body Hash**:
    *   If the request has a body (e.g., POST, PUT), convert the JSON body to a canonical string (e.g., ensure consistent whitespace, key ordering).
    *   Calculate the SHA256 hash of this canonical request body. The hash should be lowercase hex-encoded.
    *   If the request has no body (e.g., GET, or POST with an empty body), use the SHA256 hash of an empty string: `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.
4.  **Construct the Signing String**: Concatenate the following components, each on a new line:
    *   The HTTP method in uppercase (e.g., `POST`, `GET`).
    *   The canonical URL path (the path segment of the URL, without the base URL or query parameters, e.g., `/integrations/payfactor/aels/escrows/es_f8b4e7d2-a0e1-4c3b-9d6a-5b0c1e2f3a4b/deposit-tranche1`).
    *   The canonical query string (if any). Parameters should be sorted alphabetically by key, and URL-encoded (e.g., `param1=value1&param2=value2`). If no query parameters, use an empty string.
    *   The value of the `X-PaySurity-Timestamp` header.
    *   The value of the `X-PaySurity-Tenant-Id` header.
    *   The SHA256 hash of the request body (from step 3).
5.  **Calculate HMAC-SHA256 Signature**:
    *   Use your `API_SECRET` as the key.
    *   Calculate the HMAC-SHA256 hash of the `Signing String` (from step 4).
    *   The result should be lowercase hex-encoded.
6.  **Add to Headers**: Include the calculated signature in the `X-PaySurity-HMAC-Signature` header of your API request.

### Pseudocode Example (Node.js)

```javascript
const crypto = require('crypto');

function createHmacSignature(method, path, queryString, timestamp, tenantId, requestBody, apiSecret) {
    const canonicalPath = path; // e.g., /integrations/payfactor/aels/escrows/{{escrowId}}/deposit-tranche1
    const canonicalQueryString = queryString ? [...Object.keys(queryString)].sort().map(key => `${key}=${encodeURIComponent(queryString[key])}`).join('&') : '';

    const bodyHash = requestBody
        ? crypto.createHash('sha256').update(JSON.stringify(requestBody)).digest('hex')
        : 'e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855'; // SHA256 of empty string

    const signingString = [
        method.toUpperCase(),
        canonicalPath,
        canonicalQueryString,
        timestamp,
        tenantId,
        bodyHash
    ].join('\n');

    const hmac = crypto.createHmac('sha256', apiSecret);
    hmac.update(signingString);
    return hmac.digest('hex');
}

// Example usage for a POST request:
const method = 'POST';
const path = '/integrations/payfactor/aels/escrows';
const queryString = {}; // No query params for this example
const timestamp = new Date().toISOString(); // e.g., "2023-10-26T10:30:00.000Z"
const tenantId = 'your_tenant_id_here';
const apiKey = 'your_api_key_here';
const apiSecret = 'your_api_secret_here';

const requestBody = {
    "externalRefId": "AELS-PROJ-TXN-2023001",
    "totalAmount": 1500.00,
    "tranche1Amount": 500.00,
    "currency": "USD",
    "buyerDetails": { /* ... */ },
    "sellerDetails": { /* ... */ },
    "description": "..."
};

const signature = createHmacSignature(method, path, queryString, timestamp, tenantId, requestBody, apiSecret);

// Then include in headers:
// X-PaySurity-Tenant-Id: tenantId
// X-PaySurity-API-Key: apiKey
// X-PaySurity-Timestamp: timestamp
// X-PaySurity-HMAC-Signature: signature
```

### Critical Considerations:
*   **Timestamp Skew**: The `X-PaySurity-Timestamp` must be closely synchronized with PaySurity's server time. Requests with a timestamp too far in the past or future will be rejected (e.g., +/- 5 minutes).
*   **Body Canonicalization**: For POST/PUT requests, ensure the JSON request body is stringified consistently before hashing. This typically means no pretty-printing, stable key order, and no extraneous whitespace. Many JSON libraries offer a way to get a canonical string representation.
*   **Case Sensitivity**: HTTP methods must be uppercase. Hex-encoded hashes and signatures should be lowercase.

| Code                        | HTTP Status | Description                                                                   | Resolution Steps                                                                                                                                                                 |

## Sandbox Testing Guide

PaySurity provides a dedicated sandbox environment for PayFactor to develop and test its integration without affecting live production data or real funds.

### 1. Sandbox Environment Setup

*   **Access Credentials**: Obtain your sandbox-specific `TENANT_ID`, `API_KEY`, and `API_SECRET` from your PaySurity account manager or the PaySurity developer portal. These are distinct from production credentials.
*   **Base URL**: The sandbox API base URL will be different (e.g., `https://api.sandbox.paysurity.com`).
*   **Webhook Configuration**: Configure your webhook endpoint in the sandbox environment settings on PaySurity (or provide it to your PaySurity contact). Ensure your webhook receiver is accessible from the public internet.

### 2. Key Test Cases

Thoroughly test the following scenarios to ensure your integration behaves as expected:

*   **Successful 2-Tranche Flow**:
    1.  Create Escrow (`POST /escrows`).
    2.  Deposit Tranche 1 (`POST /escrows/{id}/deposit-tranche1`).
    3.  Deposit Tranche 2 (`POST /escrows/{id}/deposit-tranche2`).
    4.  Release Funds (`POST /escrows/{id}/release`).
    5.  Verify final status (`GET /escrows/{id}`) is `COMPLETED`.
    6.  Verify all corresponding webhooks (`escrow.created`, `escrow.tranche1.funded`, `escrow.tranche2.funded`, `escrow.completed`).

*   **Tranche 1 Refund Flow**:
    1.  Create Escrow.
    2.  Deposit Tranche 1.
    3.  Refund Tranche 1 (`POST /escrows/{id}/refund-tranche1`).
    4.  Verify final status (`GET /escrows/{id}`) is `REFUNDED_TR1`.
    5.  Verify corresponding webhooks (`escrow.created`, `escrow.tranche1.funded`, `escrow.refunded.tranche1`).

*   **Error Handling - Invalid State**:
    1.  Attempt to deposit Tranche 2 before Tranche 1 is funded (should return `INVALID_ESCROW_STATE`).
    2.  Attempt to release funds before both tranches are funded (should return `INVALID_ESCROW_STATE`).
    3.  Attempt to refund Tranche 1 after Tranche 2 is funded or funds have been released (should return `INVALID_ESCROW_STATE`).
    4.  Attempt to deposit an amount for a tranche that doesn't match the expected amount (`AMOUNT_MISMATCH`).

*   **Authentication & Authorization Errors**:
    1.  Send a request with a missing or invalid `X-PaySurity-API-Key` (`INVALID_API_KEY`).
    2.  Send a request with a deliberately incorrect `X-PaySurity-HMAC-Signature` (`INVALID_HMAC_SIGNATURE`).
    3.  Send a request with a timestamp far from current UTC (`TIMESTAMP_SKEW_TOO_LARGE`).
    4.  Attempt to access an escrow belonging to another tenant (if possible, this should result in `FORBIDDEN` or `NOT_FOUND`).

*   **Idempotency (if applicable)**:
    1.  Resend a successful Tranche 1 deposit request with the exact same payload and signature. Ensure it doesn't cause a duplicate event or error out idempotently. PaySurity APIs are generally designed to be idempotent.

*   **Webhook Verification**:
    1.  For every event, verify the `X-PaySurity-Webhook-Signature` header using your `Webhook Secret`.
    2.  Ensure your webhook endpoint properly acknowledges receipt with a `2xx` status code.
    3.  Test webhook retries by temporarily failing your webhook endpoint (e.g., return `500` or time out) and observe if PaySurity retries the event.

### 3. Monitoring and Logging

*   **PaySurity Dashboard**: The PaySurity dashboard provides detailed logs of all API requests and webhook deliveries for your sandbox tenant. Use this to debug issues and verify expected behavior.
*   **Your System Logs**: Ensure your application logs all outgoing API requests to PaySurity (request body, headers, response) and all incoming webhook events for auditing and debugging.

## Production Checklist

Before deploying your PayFactor AELS integration to production, review and complete the following checklist:

### Security & Credentials
*   [ ] **Production Credentials**: Use your *production-specific* `TENANT_ID`, `API_KEY`, `API_SECRET`, and `Webhook Secret`. **Never use sandbox credentials in production.**
*   [ ] **Secret Management**: Ensure API keys and secrets are securely stored (e.g., environment variables, secret management service) and never hardcoded or exposed in source control.
*   [ ] **HMAC Implementation**: Double-check your HMAC signing logic against the provided instructions and pseudocode. A small deviation can lead to authentication failures.
*   [ ] **Webhook Verification**: Implement webhook signature verification in your production webhook receiver. This is crucial for security.
*   [ ] **HTTPS Only**: All communication with PaySurity, both API requests and webhook callbacks, must use HTTPS.

### Configuration & Networking
*   [ ] **Production Base URL**: Ensure your API calls target the production PaySurity API base URL (e.g., `https://api.paysurity.com`).
*   [ ] **Webhook Endpoint**: Configure your production webhook URL in the PaySurity dashboard. This URL must be publicly accessible via HTTPS.
*   [ ] **Firewall/Network Rules**: If your systems are behind a firewall, ensure that outbound connections to PaySurity API endpoints and inbound connections from PaySurity webhook servers are permitted.
*   [ ] **IP Whitelisting (Optional)**: If you require stricter security, discuss IP whitelisting options with PaySurity support for both outbound API calls and inbound webhooks.

### Error Handling & Monitoring
*   [ ] **Comprehensive Error Handling**: Implement robust error handling for all PaySurity API responses, including `4xx` and `5xx` errors.
*   [ ] **Retry Logic**: Implement idempotent retry mechanisms with exponential backoff for transient errors (e.g., `5xx` status codes, network timeouts).
*   [ ] **Alerting**: Set up monitoring and alerting for API errors, failed webhook deliveries, and unexpected transaction states.
*   [ ] **Logging**: Ensure all API requests/responses and webhook events are logged for debugging and auditing purposes in your production environment.
*   [ ] **Reconciliation**: Establish a daily or periodic reconciliation process to compare transaction states in PayFactor with PaySurity records, especially for long-running escrow transactions.

### Performance & Scalability
*   [ ] **Rate Limiting**: Be aware of and design for PaySurity's API rate limits. Implement appropriate retry mechanisms or queueing if your call volume is high.
*   [ ] **Asynchronous Processing**: For webhook events, consider processing them asynchronously to ensure your endpoint responds quickly and avoids timeouts.

### Operational Procedures
*   [ ] **Support Contacts**: Have clear internal procedures for escalating issues and contacting PaySurity support.
*   [ ] **Disaster Recovery**: Plan for scenarios where PaySurity or your systems might be temporarily unavailable.
*   [ ] **Documentation**: Ensure your internal documentation for the PaySurity integration is up-to-date and accessible to your operations and support teams.
